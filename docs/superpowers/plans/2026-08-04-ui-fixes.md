**Interfaces:**
- Consumes: none (no external dependency for this task).
- Produces: `ModalDialog` (existing default export, same props: `title`, `onClose`, `children`, `style?`, `className?`, `autoFocus?`) plus a new named export `ModalPortal` (`{ onClose: () => void; children: ReactNode; autoFocus?: boolean }`) — the shared, chrome-free portal+inert+focus+Escape primitive that `ModalDialog`, `ConfirmDialog`, and `TruncateDialog` all build on. `ConfirmDialog`/`TruncateDialog` keep their existing public props (`message`/`onConfirm`/`onCancel` and `label`/`onConfirm`/`onCancel` respectively) — only their internal implementation changes, so none of their ~10 call sites across `ui/src/routes/**` need edits. Task 6 (`AddMatcherModal` in `ui/src/routes/topics/$topic.tsx`) consumes `ModalDialog` from this task.

**Root cause:** In all four files, `aria-hidden="true"` sits on the **overlay** `<div>` that *wraps* the dialog panel (`<div className="jx-overlay" ... aria-hidden="true"><div role="dialog" ...>`). Since `aria-hidden` hides the entire subtree, this makes the dialog panel — and every field and button inside it — invisible to assistive technology, the exact opposite of the doc comment's claim ("Overlay is aria-hidden so assistive technology only reads the dialog"). None of the modals are rendered through a React portal today; they render inline wherever the parent route puts them, with `position: fixed` doing the visual overlay work. Because they aren't portaled, there is no true DOM sibling to mark inert instead — the fix below introduces a portal specifically so background content becomes a real sibling that *can* be safely hidden.

**Design:** Add a `ModalPortal` primitive to `ModalDialog.tsx` that: (1) portals its children to a dedicated `<div id="jx-modal-root">` appended once to `document.body`; (2) while mounted, marks every *other* child of `document.body` (in practice, the app root) with both `inert` and `aria-hidden="true"` — belt-and-suspenders, since `inert`'s accessibility effects aren't universally implemented across every browser/AT combination, and this is standard practice for accessible modal implementations; (3) reference-counts open modals (module-level `openModalCount`) so background is only restored once the last modal closes; (4) keeps the existing focus-first-focusable-element-on-mount and Escape-closes behavior. Because `inert` blocks focus and pointer events on everything outside the portal, **this is also the focus trap** — Tab can never reach the background while a modal is open, so no manual Tab/Shift-Tab interception is needed (this directly answers the brief's question of whether a focus trap already exists to reuse: it does not today, but `ModalPortal`'s `inert` background *becomes* one for free, and Task 6 reuses it for `AddMatcherModal` instead of hand-rolling one).

`ModalDialog` (title + panel chrome) is rebuilt on top of `ModalPortal`. `ConfirmDialog` and `TruncateDialog` — whose content doesn't fit `ModalDialog`'s "title-is-an-`<h2>`" shape (a confirm dialog's whole point is a body-text question, not a heading, and forcing it into `<h2>`/18px/bold would look wrong for longer messages) — use `ModalPortal` directly, keeping their own overlay/panel/heading layout unchanged, gaining only the portal+inert+focus+Escape fix. This fixes the bug exactly once, in one primitive, reused three different ways — matching the brief's preference for a single shared fix over four duplicated ones, while respecting that the four dialogs don't (and shouldn't) share identical markup.

**Known, pre-existing, out-of-scope edge case (documented, not fixed here):** `ui/src/components/Toast.tsx` renders inline (not portaled) and several mutation `onSuccess` handlers call `addToast(...)` *before* `onClose()` (e.g. `AddTopicModal.tsx` line 31 then 32). Since the modal is still mounted for that one tick, a toast fired at that instant would briefly render into the now-inert background before the parent's next render unmounts the modal. This is a pre-existing ordering quirk unrelated to the `aria-hidden` bug and applies equally to any inert-background approach; not addressed by this task.

- [ ] 3. Implement the fix. Replace `ui/src/components/ModalDialog.tsx` in full:

  ```tsx
  import { useEffect, useId, useRef, type ReactNode } from 'react'
  import { createPortal } from 'react-dom'

  interface ModalDialogProps {
    title: string
    onClose: () => void
    children: ReactNode
    /** Additional styles forwarded to the inner modal panel. */
    style?: React.CSSProperties
    /** CSS class forwarded to the inner modal panel (default: "jx-modal"). */
    className?: string
    /** Focus the first interactive element automatically (default: true). */
    autoFocus?: boolean
  }

  // Portal target for every modal overlay in the app. Lazily created and
  // appended directly to <body> so that a modal's DOM subtree is always a
  // true sibling of the app root, never a descendant of it — that
  // separation is what lets us mark the app root (and everything else in
  // <body>) inert while a modal is open, without ever touching the modal's
  // own subtree.
  let modalPortalRoot: HTMLDivElement | null = null
  function getModalPortalRoot(): HTMLDivElement {
    if (!modalPortalRoot) {
      modalPortalRoot = document.createElement('div')
      modalPortalRoot.id = 'jx-modal-root'
      document.body.appendChild(modalPortalRoot)
    }
    return modalPortalRoot
  }

  // Reference-counted so that if a second modal is ever opened while one is
  // already open (e.g. a confirm dialog stacked on a form modal), the
  // background is only restored once the last modal closes.
  let openModalCount = 0
  function setBackgroundInert(inert: boolean) {
    const portalRoot = getModalPortalRoot()
    for (const child of Array.from(document.body.children)) {
      if (child === portalRoot) continue
      if (inert) {
        // `inert` (native attribute) removes the subtree from focus,
        // pointer events, and the accessibility tree in one step.
        // `aria-hidden` is set alongside it for assistive-tech/browser
        // combinations that don't yet honour `inert`'s a11y effects.
        child.setAttribute('inert', '')
        child.setAttribute('aria-hidden', 'true')
      } else {
        child.removeAttribute('inert')
        child.removeAttribute('aria-hidden')
      }
    }
  }

  interface ModalPortalProps {
    onClose: () => void
    children: ReactNode
    /** Focus the first interactive element automatically (default: true). */
    autoFocus?: boolean
  }

  /**
   * Low-level accessible modal primitive: portals `children` to a dedicated
   * <body>-level node, marks the rest of <body> inert + aria-hidden while
   * mounted, focuses the first focusable element inside on mount, and closes
   * on Escape. Renders no chrome of its own (no overlay background, no
   * panel, no title) — callers own their layout. `ModalDialog` below is the
   * title+panel flavour built on top of this; `ConfirmDialog` and
   * `TruncateDialog` use this directly because their content doesn't fit
   * ModalDialog's title-as-<h2> shape.
   *
   * Because the rest of the document is inert while this is mounted, focus
   * can never leave the portaled subtree via Tab/Shift-Tab — that doubles
   * as the focus trap, with no manual key interception required.
   */
  export function ModalPortal({ onClose, children, autoFocus = true }: ModalPortalProps) {
    const panelRef = useRef<HTMLDivElement>(null)

    useEffect(() => {
      openModalCount += 1
      if (openModalCount === 1) setBackgroundInert(true)
      return () => {
        openModalCount -= 1
        if (openModalCount === 0) setBackgroundInert(false)
      }
    }, [])

    useEffect(() => {
      if (autoFocus) {
        const first = panelRef.current?.querySelector<HTMLElement>(
          'input:not([disabled]), select:not([disabled]), textarea:not([disabled]), button:not([disabled]), [tabindex]:not([tabindex="-1"])'
        )
        first?.focus()
      }

      const onKey = (e: KeyboardEvent) => { if (e.key === 'Escape') onClose() }
      document.addEventListener('keydown', onKey)
      return () => document.removeEventListener('keydown', onKey)
    }, [onClose, autoFocus])

    return createPortal(<div ref={panelRef}>{children}</div>, getModalPortalRoot())
  }

  /**
   * Accessible modal overlay wrapper — title + panel chrome on top of
   * ModalPortal.
   *
   * - Renders through ModalPortal: a true <body>-level sibling of the app
   *   root, with the app root marked inert + aria-hidden while open. The
   *   dialog's own subtree is never aria-hidden — assistive technology
   *   reads it normally.
   * - Inner panel has role="dialog", aria-modal="true", aria-labelledby
   *   pointing at the title.
   * - Escape key closes the dialog.
   * - Focus is moved to the first focusable element inside on mount.
   */
  export function ModalDialog({
    title,
    onClose,
    children,
    style,
    className = 'jx-modal',
    autoFocus = true,
  }: ModalDialogProps) {
    const titleId = useId()

    return (
      <ModalPortal onClose={onClose} autoFocus={autoFocus}>
        <div className="jx-overlay" onClick={onClose}>
          <div
            role="dialog"
            aria-modal="true"
            aria-labelledby={titleId}
            className={className}
            style={style}
            onClick={(e) => e.stopPropagation()}
          >
            <h2 id={titleId} style={{ margin: '0 0 1.25rem', fontSize: 18, fontWeight: 700 }}>{title}</h2>
            {children}
          </div>
        </div>
      </ModalPortal>
    )
  }
  ```

**Root cause (verified by reading the full file):** `RuledTable` (lines 1020–1082) maps every row in `table.getRowModel().rows` to a `<tr>` with no windowing — for the matcher table this is harmless (typically a handful of rows), but the same component renders the main records table (line 860), which can hold thousands of streamed rows. Separately, `streamBufferRef.current` (declared line 178) accumulates every record for the life of a `follow=true` SSE/NDJSON session with no cap, and is copied wholesale into React state every 250ms (`setStreamedRecords([...streamBufferRef.current])`, three call sites: lines 289, 326, 333). When `order=desc` and follow-live is active, new records are prepended via `streamBufferRef.current.unshift(r)` (line 310) — `unshift` re-indexes the entire array on every call, so incoming-record cost grows linearly with buffer size, i.e. O(n) per record / O(n²) over a session, independent of the (also real, but linear-in-ticks-not-quadratic) cost of the 250ms flush copy.

**Design:**
1. **Buffer cap + O(1) push**, in a new pure module `ui/src/lib/streamBuffer.ts` (DOM-free, unit-testable under the default `node` Vitest environment, no jsdom pragma needed):
   - `pushCapped(buffer, record)` appends in place, then, only once `buffer.length` exceeds `MAX_LIVE_TAIL_BUFFER + LIVE_TAIL_TRIM_BATCH`, drops the oldest excess in one `splice` call so the buffer settles back to exactly `MAX_LIVE_TAIL_BUFFER`. The `splice` is O(k), but runs only once per `LIVE_TAIL_TRIM_BATCH` (500) pushes — amortized O(1) per record, same technique as a geometrically-growing array, applied in reverse for eviction.
   - `composeDescLiveView(historyBuffer, liveBuffer)` replaces the `unshift` path. During history drain (before the `follow` preamble), records keep being `.push()`-ed directly onto `streamBufferRef.current` as today (drain is already bounded by the request's own `from`/`to`/`limit`, not by this cap — capping it too could silently drop data the user explicitly asked for). Once `follow` is active, new records for the `order=desc` case are pushed (not unshifted) onto a **second**, separate `liveBufferRef.current` array in arrival order. The rendered/flushed view is composed on demand: `composeDescLiveView` reverses only the (now-bounded, ≤5500-element) live segment and concatenates it in front of the already-correctly-ordered history segment. This reverse is O(live-segment-length) and runs once per 250ms flush tick — linear in ticks, never quadratic, and bounded by the same cap.
   - The `order=asc` follow-live case (plain append, no prepend) is also capped via `pushCapped` directly on `streamBufferRef.current` once `followActiveRef.current` is true, addressing the brief's broader "grows unbounded for the life of a follow=true session" concern, not just the `unshift` case specifically.
2. **Virtualization**: `RuledTable`'s `<tbody>` switches from rendering every row to rendering only the rows `@tanstack/react-virtual`'s `useVirtualizer` reports as visible (plus overscan), using the "padding-row" technique (two placeholder `<tr>`s sized to the skipped space above/below the visible window) rather than absolute-positioning every `<tr>`, so the real `<table>`/`<thead>`/`<tbody>` semantics and column alignment are preserved (an absolutely-positioned-row/flex-tbody layout, the other common virtualization pattern, would require abandoning native table layout and was rejected as unnecessarily risky for this fix).   // Pure helpers for the live-tail record buffer used by the topic replay
  // stream (src/routes/topics/$topic.tsx). Kept dependency-free so they can
  // be unit tested without touching the DOM or mocking EventSource/fetch.

  /** Hard cap on how many records the live-tail buffer holds once follow=true
   *  tailing is active. Historical drain (before the `follow` preamble) is
   *  not capped here — that's already bounded by the query's own
   *  from/to/limit params. */
  export const MAX_LIVE_TAIL_BUFFER = 5000

  /** How many records to trim in one batch once the cap is exceeded, so the
   *  O(n) splice only runs once every N pushes instead of on every push —
   *  amortized O(1) per record. */
  export const LIVE_TAIL_TRIM_BATCH = 500

  /** Push `record` onto `buffer` in place, then, if the buffer has grown
   *  past MAX_LIVE_TAIL_BUFFER + LIVE_TAIL_TRIM_BATCH, drop the oldest
   *  excess in a single splice so the buffer settles back to
   *  MAX_LIVE_TAIL_BUFFER. */
  export function pushCapped<T>(buffer: T[], record: T): void {
    buffer.push(record)
    if (buffer.length > MAX_LIVE_TAIL_BUFFER + LIVE_TAIL_TRIM_BATCH) {
      buffer.splice(0, buffer.length - MAX_LIVE_TAIL_BUFFER)
    }
  }

  /** Compose the buffer to render for order=desc + follow=true tailing,
   *  where live records must visually prepend (newest-first) without ever
   *  doing an O(n) unshift per incoming record. `liveBuffer` holds live
   *  records in arrival order (oldest-of-the-live-batch first);
   *  `historyBuffer` holds the already-drained history, already in the
   *  correct newest-first order. */
  export function composeDescLiveView<T>(historyBuffer: T[], liveBuffer: T[]): T[] {
    if (liveBuffer.length === 0) return historyBuffer
    return [...liveBuffer].reverse().concat(historyBuffer)
  }

**Root cause (verified by reading the full file):** `MetricsPage`'s `useEffect` (lines 562–566) calls `poll()` immediately, then `setInterval(() => { void poll() }, POLL_MS)` (3000ms) unconditionally for the component's lifetime — polling continues at full cadence even when the browser tab is backgrounded, wasting network/CPU. `TopicRow` (lines 378–422) computes `lagSeries`, `rateSeries`, and `netPts` as plain `.map()` calls in the function body with no `useMemo`, so they rebuild on every render of `TopicRow` regardless of whether `pts`/`partitions`/`label`/`tk` actually changed. **Design:**
1. **Pause on hidden tab**: `useVisibilityAwareInterval(callback, intervalMs)` runs `callback` on the normal interval while `document.visibilityState !== 'hidden'`, clears the interval entirely while hidden, and — on `visibilitychange` back to visible — calls `callback` immediately (catch-up fetch) before resuming the interval. `MetricsPage` keeps its own one-time `useEffect(() => { void poll() }, [])` for the initial mount fetch, and replaces the manual `setInterval`/`timerRef` block with this hook.
2. **Memoize `pts` first, in the parent**: without this, `useMemo` inside `TopicRow` is close to useless, since its `pts` dependency would still change reference on every parent render regardless of whether `history` changed (the failed-poll scenario above proves this is a real, not theoretical, case). `pts` becomes `useMemo(() => history.map(...), [history])` in `MetricsPage`.
3. **Extract + memoize the three derived arrays** in `TopicRow`: move the pure computation logic to `ui/src/lib/metricsDerive.ts` (testable without React/DOM), then wrap each call in `useMemo` with an honest, minimal dependency list, and wrap `TopicRow` itself in `React.memo` so an unrelated parent re-render with unchanged props skips re-invoking the row entirely (deepest available protection, on top of the `useMemo` calls, which still protect the case where `TopicRow`'s props changed for reasons unrelated to `pts`/`partitions`/`label`/`tk` specifically — e.g. a future prop addition).

  import { useEffect, useRef } from 'react'

  /**
   * Like setInterval, but pauses while the document is hidden (backgrounded
   * tab) instead of continuing to fire, and — on becoming visible again —
   * fires one immediate catch-up call before resuming the normal cadence.
   */
  export function useVisibilityAwareInterval(callback: () => void, intervalMs: number): void {
    const callbackRef = useRef(callback)
    useEffect(() => { callbackRef.current = callback }, [callback])

    useEffect(() => {
      let timer: ReturnType<typeof setInterval> | null = null

      function start() {
        if (timer == null) timer = setInterval(() => callbackRef.current(), intervalMs)
      }
      function stop() {
        if (timer != null) { clearInterval(timer); timer = null }
      }
      function handleVisibilityChange() {
        if (document.visibilityState === 'hidden') {
          stop()
        } else {
          callbackRef.current() // catch-up fetch on resume
          start()
        }
      }

      if (document.visibilityState !== 'hidden') start()
      document.addEventListener('visibilitychange', handleVisibilityChange)
      return () => {
        stop()
        document.removeEventListener('visibilitychange', handleVisibilityChange)
      }
    }, [intervalMs])
  }
